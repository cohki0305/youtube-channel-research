# YouTubeチャンネル リサーチ

## ゴール

1. **チャンネルとして、なぜ伸びているのかを分析する**（パートA）
2. **チャンネルから見つかったキーワードの検索結果を見て、分析する**（パートB）
3. **自分（クライアント）のチャンネルで、なぜこの動画は伸びて、あの動画は伸びなかったのかを検証する**（パートC）

どちらも、Claudeが分析するだけでなく、**運用者（ユーザー）が同じ分析を自分でできるように考えさせる**。最終的に、運用者がクライアントに「このチャンネルはこういう理由で伸びている。このキーワードではこういう動画が勝っている。だから、あなたのチャンネルはこう伸ばせる」を、データを根拠に説明できるようにする。

**進め方の核**：仮説を立てる → データで反証・確認する → 台帳に残す → 別のチャンネルやキーワードで確かめる。

## 原則

- **チャットには要点だけを書く。** 細かいデータ（全動画の表、エージェントの全文など）はファイルに置く。形式の決まり（見出しの数や行数）よりも、各段階の「返答に入れるもの」と品質の確認を優先する
- **理由はすべて仮説として書き、番号をつける**（例：H3）。検証した結果（支持・否定・保留）を添える
- **数字には出典を書く**（YouTube API／ラッコ）。推測は推測と書く
- **題材語の種類（銘柄名・用語・時事・人名など）を混ぜて相関を出さない**
- **動画は、順位・番号・IDではなく、タイトル（リンク）で示す。** 表でも同じ。チャンネル名・再生数・尺・公開からの日数を添える。順位は補足としてだけ書く（「1位は〜」では、読む人がどの動画か分からない）
- **2026-08-27 ごろの前後をまたいで視聴回数を比べない。** この日ごろから、YouTube の視聴回数がホームの自動再生なども数えるようになったとみられ、自分のチャンネルの Analytics API で、視聴回数 ÷ エンゲージビューが 1.00 から大きく跳ねたことがある。自分のチャンネル（パートC）では、比較にエンゲージビューを使う。外部のチャンネル（パートA・B）では Data API の視聴回数しか取れないので、公開日がこの日の前か後かで分けて比べ、またぐ比較は「数え方の違いを含む」と書く（観測は1チャンネルのみ。YouTube 全体の変更かは未確認）

### ラッコの位置づけ

ラッコの検索数は **Googleの月間検索数**で、YouTube内の検索数ではない。「キオクシア 株価」（月274万）のように、検索する人の多くは株価を見たいだけで、動画を探していない。

- **パートA（チャンネル分析）では補助。** 使い道は次の3つに限る。チャンネル分析の中心は、YouTubeの動画データ（題材別の中央値、推移、上位と下位の比較）とする
  1. **推測の否定**：Claudeや運用者が挙げたキーワードに、本当に検索されている実体があるかを確かめる（例：「好決算 下落」は月30で、検索からは人を呼べない）
  2. **追い風の検出**：前年比や急増した月から、話題や相場の追い風を見る
  3. **伸び方の型の見分け**：題材語の種類ごとの相関で、「題材で伸びる型」と「人で伸びる型」を見分ける
- **相関は「関心の大きさの目安」として書く。「検索から人が来ている」とは書かない。** 流入元（検索／ブラウジング／関連動画）は、外部のチャンネルでは取れないため、どちらの経路で見られているかは決められない
- **パートB（キーワードの検索結果の分析）と企画では、中心のデータ。** YouTubeの検索結果と組み合わせて、どの言葉に関心が集まり、YouTubeでは誰が上位を取っているかを見る
- **クライアント自身のチャンネルを分析するときは、YouTube Studio のデータを優先する**（下の「準備」を参照）
- 過去のチャンネルの数値を、目安として持ち込まない。チャンネルごとに伸び方は違う

### 運用者に考えさせる（軽く）

分厚い資料で考えさせない。次の2つだけを行う。

- **返答の最後に「運用者への問い」を1〜2個置く。** データを見れば答えられて、クライアントとの会話でそのまま使える問いにする（例：「キオクシアは月274万回検索されているのに、田端大学の動画は6万回でした。なぜだと思いますか？」）
- **運用者が答えたら、短く壁打ちする。** 合っている点、見落としている点、データで確かめる方法を3〜5行で返す。正解を押しつけない

## 準備（初回のみ）

- **YouTube APIキー**：`.env` の `YOUTUBE_API_KEY` の有無だけを確認する（値は表示しない）。なければ README の手順を案内する。キーの作成・保存はユーザーが行う
- **ラッコMCP**：未接続なら、claude.ai の「設定 → コネクタ → コネクタを管理」で、ラッコキーワードのコネクタ（https://claude.ai/directory/connectors/rakkokeyword）の追加を依頼する。ライトプランは `suggest-keywords` 1回5クレジット、`search-volume-history` は50語まで1回最低50クレジット。**キャッシュ（`scripts/rakko_cache.ts`）を必ず使う**（`missing` → ラッコ → `put` → `volumes`）
- **ヒアリング**：ユーザーのチャンネル（またはクライアント）の目的・演者・体制を聞く。会話やメモリでわかっていれば聞かない。回答は A4 の判断（何が再現できて何が再現できないか）と見解で使う。A1〜A3 の事実集めと、エージェントに渡す事実には入れない
- **クライアント自身のチャンネルを分析する場合**：パートCに従う。YouTube Studio のデータと Analytics API を、ラッコの相関より優先する

## パートA：チャンネルがなぜ伸びているか

流れ：データから仮説を出す → 視聴者のニーズで読む → **自分の推測をラッコで疑い、キーワードを出し直す** → 4つの立場で判断する → 検証する。

**A1・A2は内部の作業で、ユーザーには出さない。** 最初にユーザーに見せる返答はA3とする。A1・A2の内容（基本データ、事業の構造、仮説、ニーズの読み）は、A3の返答の冒頭に要点だけ入れ、詳細は `data/<slug>/why/a1_a2.md` に残す。A3以降は、各段階の返答のあとでユーザーの反応を見てから次に進む。

### A1：初見の分析（YouTubeのデータだけで）

**データを取る**

```bash
node scripts/fetch_channel.ts @handle
node scripts/analyze_channel.ts data/<slug>
```

- 直近12か月の通常動画を、タイトルの語のルールで**機械的に**題材の種類に分ける（`data/<slug>/why/classify.ts` に残す。例は `examples/classify.example.ts`。`data/<slug>/why/` にコピーして使う）。タイトル全体で判定すると誤分類が多いときは、タイトル先頭の【】で判定する。種類ごとに本数と再生数の中央値を出す
- 概要欄から、運営会社・演者の肩書き・収益源（スポンサー、送客先、有料講座、案件の募集）を確かめる

**まとめるもの**（ユーザーには出さず、`why/a1_a2.md` に書く）

- 基本データ（登録者、本数、中央値、尺、投稿の曜日と時刻、推移）
- **事業の構造**：何で元を取っているか（広告、送客、講座、案件）。それが本数や題材の選び方にどう効いているか
- **伸びている理由（仮説）**：H1〜。根拠の数字つき。上位と下位を比べ、「有名なのに伸びない」のような直感に反する差を探す
- **真似できそうな検索キーワード（候補）**：タイトルと題材から推測したもの。**この段階ではデータで裏付けていないと明記する**

### A2：視聴者のニーズから読む（推測でよい）

- 題材の型ごとに、「視聴者がどんな状況で、何を求めて、この動画を見るか」→「このチャンネルがそれをどう満たしているか」を書く。心理学の用語は、説明が短くなるときだけ使う
- 最後に一本の筋にまとめる（例：「持ち株が心配になる → 理由がプロの言葉でわかる → 安心し、少し賢くなった気がする → また見に来る」）
- どの感情が「1回見て終わり」でなく「登録」につながっているかを書く

### A3：ラッコで出し直す（自分の推測を疑う）。ここから出力する

A1・A2を終えたら、自分に次の指示を出して実行する。

> **A1・A2で出したキーワードは、データに基づいていない。ラッコの検索キーワード（サジェスト）とボリュームを使って、真似できそうな検索キーワードを考え直す。**

**手順**

1. **A1・A2で出した語とフレーズを、全部ラッコで確かめる**（`search-volume-history`。キャッシュを先に見る：`rakko_cache.ts missing` → ラッコ → `put`）。タイトルでクリックを促すフレーズ（例：「好決算 下落」「元機関投資家」）も入れる
2. **チャンネルの題材の型ごとに、種になる語でYouTubeサジェストを取る**（`suggest-keywords`、modes: ["youtube"]。例：「株価」「銘柄」「株式分割」「好決算」）。実際に検索されている言い回しと検索数を集める
3. **題材語を種類ごとに `keywords.csv`（`video_id,keyword,type`）に書き、相関を出す**：`node scripts/correlate.ts data/<slug> --since <12か月前のYYYY-MM>`。相関は「関心の大きさの目安」として読む
4. **検索数の区分ごとに、再生数の中央値を出す**（例：70万以上／10万〜70万／10万未満）

**返答に入れるもの**

- **冒頭の要点**（A1・A2から）：基本データ（3行ほど）、事業の構造（何で元を取っているか）、伸びている理由の仮説（H1〜）、視聴者のニーズの一本の筋
- **データで否定されたもの**：A1・A2で挙げた語のうち、検索数がほぼない語をはっきり書き、「検索では人を呼べない。タイトルでクリックを促す用途に限る」と位置づけ直す
- **真似できる検索キーワード**：表（型／キーワード／月間検索数／前年比／このチャンネルでの再生数）。検索数の大きい順
- **型ごとの相関と、検索数の区分ごとの再生数**：どの型が「関心の大きさ」とつながっているか
- **タイトルの組み立て方**：検索で見つけてもらう語（データのある語）と、クリックを促す語（データのない語）の組み合わせ方
- **このチャンネルでまだ扱っていない、検索数の大きい語**
- 注意：ラッコの数値はGoogleの月間検索数で、YouTube内の検索数ではない

### A4：4つの立場で判断する（認知的多様性）

**Skillツールで `cognitive-diversity` スキルを必ず読み込み、その手順に従う。**スキルが未配置の場合は、このリポジトリの `skills/cognitive-diversity/SKILL.md` を読む。

- **問いは、判断の形にする**：「このチャンネルはなぜ伸びたか。そして、この運用者（クライアント）がゼロから始めたら、何が再現できて、何が再現できないか」。認知的多様性は判断のための手法なので、判断の問いがないと、立場ごとに理由を並べるだけになる
- **立場は次の4つ。1回のメッセージで4つのエージェントを並列に立てる**（Agentツール）。各エージェントには、A1〜A3で集めた事実（数字と出典のみ。Claudeの解釈は入れない）だけを渡し、互いの出力は見せない。Agentツールが使えない環境では、独立性が弱まることを返答の冒頭に書く

| 立場 | 設定 | 書いてもらうこと（各400字程度） |
|---|---|---|
| A | YouTubeのアルゴリズムと配信の仕組みに詳しいグロース担当。視聴者心理や事業は脇に置く | 判断基準／伸びた理由トップ3／他の立場が過大評価していそうな説明／確信できない点と必要なデータ |
| B | 金融系スタートアップでメディア事業を回した事業責任者。「中身より資本と体制で説明できる」前提 | 判断基準／伸びた理由トップ3／個人がゼロから真似できない要素／確信できない点と確かめ方 |
| C | ペルソナにあたる視聴者（例：新NISAで個別株を5〜10銘柄持つ40代会社員）。マーケティング用語を使わない | 判断基準／登録する理由トップ3／他チャンネルとの違い／見るのをやめるきっかけ |
| D | 外部環境と偶然（相場の追い風、タイミング、生存者バイアス）で説明する懐疑的なアナリスト | 判断基準／外部環境で説明できる部分／来年ゼロから始めて再現できない要素／工夫が効いているかの比較方法 |

D には、ラッコの前年比・急増した月と、年別・月別の再生数を多めに渡す。

**統合する**：見出しは cognitive-diversity スキルの「出力の型」に従う（前提と仮定／立場別の評価／反対側の最も強い論拠／プレモーテム／意見が割れる論点と決着させる方法／似た構造の事例／実際の人に聞くべき質問／私の見解）。行数や見出しの数の決まりは設けない。そのかわり、出す前に次の3点を確かめる。

1. **立場どうしの対立を解く一文があるか**：食い違って見える立場が、実はそれぞれ別のものを説明していないか。特に「チャンネル内で伸びる動画と伸びない動画の差を説明する要因」と「他のチャンネルとの差を説明する要因」を分ける（例：「題材はチャンネル内の差を、肩書きは他チャンネルとの差を説明している」）
2. **反対側の論拠が、分析の土台になっている数字の解釈そのものを攻撃しているか**（例：「相関0.71はノウハウの証拠ではなく、追い風の証拠だ」）。弱い反論を立てて倒していないか
3. **見解とプレモーテムが、この運用者（クライアント）の状況に具体的に踏み込んでいるか**：演者の肩書き、制作体制、収益の設計（事業の構造）、運用者自身の強みを前提に、「あなたが真似したら」の形で書く。一般論で止めない

最後に、運用者への問いを1個置き、「論点を確かめますか？」と聞く。

### A5：仮説を検証する

A4の論点と、A1〜A3の仮説のうち、**取得済みのデータで安く確かめられるもの**から順に検証する。

- 検証の前に、仮説ごとに「**正しければ何が見えるはずか**（予測）」を1行で書く。予測を書けない仮説は、検証の対象にしない
- 使えるデータ：`videos.json`（月別・年別・題材別・尺・高評価数）、ラッコのキャッシュと追加取得、`search_compare.ts`（同じ題材の競合動画との比較。1回約100ユニット。実行前に回数を伝える）
- 仮説ごとに「予測 → 結果（数字と出典）→ 判定（支持／否定／保留）→ 仮説の修正」を書く。最後に、修正後の「伸びている理由」をまとめ直し、運用者への問いを1個置く
- 結果を台帳に記録する

## パートB：キーワードの検索結果を分析する

パートAで見つかったキーワードについて、**YouTubeで検索したときに、誰が、どんな動画で上位にいるか**を見る。チャンネル単体では見えない「そのキーワードの競争の状況」と「入る余地」を分析する。ラッコ（関心の大きさ、前年比、言い回しの広がり）と、YouTubeの検索結果（誰が上位か）を組み合わせるのは、このパートの中心の作業になる。

### B1：キーワードを選ぶ

- A3の表の真似できる検索キーワードから、**3〜6語**を選ぶ。ユーザーの指定があれば優先する
- 選ぶ基準：チャンネルの中で再生が取れていた語、検索数が大きい語、急に検索が増えた語（前年比）、クライアントの題材に近い語。**性質の違う語を混ぜる**（例：銘柄名、話題の用語、定番の用語）
- 実行前に、語と消費ユニット（1語約100ユニット）を伝える

### B2：検索結果を取る

```bash
node scripts/search_compare.ts "キーワード" --days 365 --max 20 [--highlight @分析したチャンネル]
# 必要なら --order viewCount で再生数順も見る
# → data/_search/<語>.md / .json
```

あわせて、ラッコで各語の月間検索数・前年比と、YouTubeサジェスト（言い回しの広がり）を確かめる（キャッシュを先に見る）。

### B3：分析する

**返答の形**（キーワードごとに4〜6行。最後に全体のまとめ）

1. **キーワードごとの要約表**：語／月間検索数・前年比（ラッコ）／上位の再生数の中央値／登録者10万人未満のチャンネルの本数／開設2年以内のチャンネルの本数／直近30日の動画の本数／分析したチャンネルの順位
2. **キーワードごとの読み取り**（各2〜4行）
   - **誰が勝っているか**：大手メディア・証券会社・著名人・個人の解説者のどれが上位を占めるか
   - **何で勝っているか**：上位の動画のタイトルの型、尺、投稿の速さ（話題が出てから何日で出たか）
   - **入る余地**：登録者の少ないチャンネルや新しいチャンネルが、「再生÷登録者」の高い動画で上位にいるか
   - **検索数と再生数のずれ**：検索数が大きいのに上位の再生が少ない、またはその逆なら、なぜかの仮説（例：検索する人は株価を見たいだけで、動画を求めていない）
3. **キーワード横断のまとめ**（3〜5行）：どの型の語なら、新しいチャンネルでも入れそうか。パートAの仮説のどれを支持・否定するか
4. **運用者への問い**（1〜2個）

分析の仮説にはパートAと同じく番号（K1〜）をつけ、台帳に記録する。

## パートC：自分のチャンネルを振り返る

**チャンネル固有の実例・数字は、git の管理外に置く。** このスキルは公開リポジトリにあるため、特定のチャンネルの数字・動画ID・目的は書かない。実例は `skills/youtube-channel-research/examples.local.md`（`.gitignore` の `*.local.md`）にあれば読み、新しい実例もそこに書く。分析の結果は `data/`（管理外）に置く

運用者自身（またはクライアント）のチャンネルを、新しい視聴者とリピーターに分けて振り返り、「なぜこの動画は伸びて、あの動画は伸びなかったか」を仮説として検証する。チャンネルの持ち主の協力（ログインと Studio の書き出し）が必要になる。

- **チャンネルの前提を決めつけない。** 目的・本数・動画の種類はチャンネルごとに違う。目的はヒアリングで聞き、C3 の「何を伸びたとするか」にだけ使う
- **通常動画・ショート・ライブを混ぜない。** レポートも種類ごとに分かれている
- 数字には出典を書く（[Studio]／[API]／[文字起こし]／ラッコ）

### C0：準備（初回のみ）

- ログイン：README「自分のチャンネルを分析する」の手順（ユーザーが行う）。`.env` の `YOUTUBE_OAUTH_CLIENT_ID`・`YOUTUBE_OAUTH_REFRESH_TOKEN` の有無だけを確かめ、値は表示しない
- ヒアリング（上の「準備」と同じ）。加えて「**このチャンネルで何を伸ばしたいか**」を聞く（例：新しい視聴者を増やしたい／リピーターを育てたい／登録者を増やしたい／問い合わせ・契約を増やしたい）
- 目的が問い合わせ・契約なら、**問い合わせや相談の傾向**も聞く（どの題材・道具について聞かれることが多いか、どんな悩みか）。YouTube のデータでは見えない、契約に近い悩みの手がかりになる

### C1：データを揃える

```bash
node scripts/fetch_channel.ts @handle
node scripts/fetch_own_analytics.ts data/<slug> [--since YYYY-MM]
node scripts/import_studio.ts data/<slug>      # Studio の CSV を own/studio/all/ に置いてから（書き出しはユーザーに頼む）
node scripts/fetch_transcript.ts data/<slug> --ids a,b,c   # 比べる動画だけ（非公式の通信。20本を超えるときは確認してから --yes）
node scripts/own_keywords.ts data/<slug>       # YouTube検索語（Analytics API）を keywords.csv に書き出す
# ここで、動画ごとの題材語を keywords.csv に種類「題材語」で足す。母数の語（例：「エクセル」）と切り口の語（例：「excel ai」）の両方（C5）
node scripts/rakko_cache.ts missing data/<slug> # キャッシュにない語だけ → ラッコ search-volume-history（aggregationPeriodMonths: 24）→ put → volumes
node scripts/analyze_own.ts data/<slug>        # → own/report.md
```

**Studio の書き出し**（ユーザーに頼む）：詳細モード →「コンテンツ」タブ → 書き出し（CSV）。期間は**すべての動画が入る長さ**にする（レポートは Studio の数字を公開からの通算として扱う）。表には動画ごとの「新しい視聴者数」「リピーター」（人数）が入るが、**365日など長い期間では空欄になる**（2026-09時点。90日なら入った）。空欄なら、すべての動画が入る範囲で短い期間を試す。公開から90日を超える動画があるときは、通算用（長い期間）と人数用（90日）の2回に分けて書き出す必要がある。`import_studio.ts` が「列が見つかりません」と出したら、実際の列名を `scripts/own/studio_csv.ts` の `STUDIO_COLUMNS` に足す。

**数字の読み方の注意**

- **再生数とエンゲージビュー**：YouTube の「視聴回数」（API の `views`）は、ホームの自動再生なども数える。平均視聴時間・平均視聴率は**エンゲージビュー1回あたり**。「総視聴時間 ÷ 視聴回数」で平均を出さない（短く出る）。**動画どうしの比較はエンゲージビューで行う**：視聴回数は、自動再生などを数えるようになった時期の前後で比べられない（2026-08-27 ごろから、視聴回数 ÷ エンゲージビューが 1.00 から跳ねた例がある）。レポートの比較・順位・順位相関はエンゲージビューを使う
- **流入元**：API の `SUBSCRIBER` は、Studio の「ブラウジング機能」（ホーム・登録チャンネルのフィード）にあたる。「登録者から来た」と読まない
- **新規の割合**：Studio の人数から出す。動画ごとの人数を足したチャンネル全体の割合は、同じ人が複数の動画を見ると重複するので、高めに出る
- **比べ方**：通算の数は公開時期で大きさが変わるので、判断には率と「公開後の同じ日数の数」（48時間・7日・28日）だけを使う
- **維持率は形で見る**（決まった秒で区切らない。落ち着く時点は動画ごとに違う）：決まった時点（0:30／1:00／2:00／5:00）の維持率、区分線形回帰で求めた「落ち着いた時点」とその水準・以降の落ち方（pt/分）、YouTube の相対評価（同じ長さの動画との比較、0.5が平均）。急な離脱・見返しは、その動画のふだんの落ち方と比べたロバストZスコア（|z|>3.5）
- **ラッコの位置づけ**（パートAと同じ）：ラッコの月間検索数は Google のもので、YouTube内の検索数ではない。どの経路で見られたかは Analytics API の流入元でわかる。**ラッコの数字を「検索から人が来た」根拠にしない。** 題材の検索数は、悩みの多さ（関心の大きさ）の目安として読む（C5）。ラッコは50語ごとにクレジットがかかるので、送る語の数を決めてから送る（`own_keywords.ts --top` で検索語の数を調整する）

### C2：1本を振り返る

ユーザーが動画を指定したとき、または C3 で比べる上位・下位の動画について行う。

```bash
node scripts/fetch_own_analytics.ts data/<slug> --video <id>
node scripts/fetch_transcript.ts data/<slug> --video <id>
node scripts/analyze_own.ts data/<slug> --video <id>   # → own/videos/<id>.md
```

**返答に入れるもの**

- 公開後の推移：48時間・7日・28日のどこで、同じ種類の中央値と差がついたか
- 流入元：どの経路で見られたか。検索なら語（とラッコの月間検索数）、関連動画ならどの動画の横か
- 新しい視聴者とリピーター：新規の割合、クリック率とインプレッションの規模
- 維持率の形：落ち着いた時点とその水準、急な離脱と見返された場所。そのとき話していた内容を文字起こしから引用する。**なぜ離脱したかは仮説として書く**
- 運用者への問い 1個

### C3：伸びた理由を仮説検証する

0. **何を「伸びた」とするかを決める**：C0 で聞いた目的から、重く見る指標を決めて書く（例：新しい視聴者を増やしたい → 新規の再生数とブラウジング機能からの流入、リピーターを育てたい → リピーターの平均視聴率、登録者を増やしたい → 登録者の増加）。既定は公開7日時点のエンゲージビュー
1. **伸びた・伸びなかったを分ける**：同じ種類の動画の中で、公開7日時点の指標で並べる（同じ日数なので公平）。7日に達していない動画は外す。公開7日のデータがある動画が10本未満なら上位と下位の数本を、10本以上なら `report.md` の「上位・下位の比較」（4分の1ずつ）を使う
2. **差を並べる**：上位と下位で、流入元・新規の割合・クリック率とインプレッションの規模・維持率の形・急な離脱とその時の発言・題材（母数の語と切り口の語の月間検索数、C5 の悩みの種類）を並べる。本数が10本以上なら、`report.md` の順位相関も見る（p<0.05 でも本数が少ないうちは偶然のことがある）
3. **仮説を立てる（O1〜）**：それぞれに「正しければ何が見えるはずか」を1行で書く。予測を書けない仮説は検証の対象にしない
   - まず流入元で絞る。ブラウジング機能・関連動画で伸びたならサムネ・タイトル・冒頭と、題材の悩み（どの母数の語の、どんな種類の悩みに答えたか）を、検索で伸びたなら検索語と題材を見る
   - **新しい視聴者に広がっても数字が落ちないかを見る。** 新しい視聴者に届くほど、クリック率も平均視聴時間も下がるのが普通。新規の割合が高く、インプレッションが大きいのに、クリック率と維持率が他の動画と同じくらいなら、**テーマへの関心が強く（クリック率に出る）、動画としての質も高い（維持率に出る）**ことの候補になる
   - 確かめ方：インプレッションの規模とクリック率を並べる（広げたのに落ちていないか）。公開直後（1〜2日目）と、おすすめで広がった後（8〜28日目）の維持率を比べる（Analytics API の維持率は期間を指定して取れる）。新規／リピーター別の平均視聴率があれば、新規の数字がリピーターに近いかを見る
   - 対立仮説も書く：おすすめが届け先を学習した結果、数字が保たれただけかもしれない（内容の強さと区別する）
4. **今あるデータで確かめる**：予測 → 結果（数字と出典）→ 判定（支持／否定／保留）→ 仮説の修正、を書く。本数が少ないと多くが「保留」になる。**そう正直に書く**
5. **返答の最後に**、運用者への問いを1〜2個置く。運用者が仮説を出したら、合っている点・見落としている点・データでの確かめ方を返し、台帳に書く

### C4：次の動画で確かめる

- 保留の仮説から1つ選び、次の動画の企画で試す（題材は C5 で探す）
- **公開前に**台帳へ書く：仮説番号（O1〜）、次の動画で変えること、予測（指標・時点・中央値との差。例：「インプレッション10万回を超えても、クリック率4.5%以上を保つ」）
- 公開7日後に C2 を回して判定し、台帳を更新する。本数が少ないうちは、これがいちばん確かな検証になる

仮説は、パートA・Bと同じ台帳に、自分のチャンネルの仮説として記録する（番号は O1〜。ベンチマークの H・K と区別する）。

### C5：次の題材を探す（検索語から悩みを汲み取る）

検索語は、悩みの表れであって、答え（動画の題材そのもの）ではない。検索数の大きい語から「なぜこの人は検索したのか、何に困っているのか」を読み取り、**その悩みを解く動画**を作る。

**全体の流れ**：母数の語を選ぶ（1）→ YouTube の上位で悩みの種類を確かめる（2）→ 上位の動画の冒頭・コメントから悩みの型を拾う（2b）→ 上位5本の全文を読み、悩みの型ごとに応えきれているかを突き合わせる（2c）→ 空白・浅い・ずれ・古い所に、運用者の知見で答える企画にする（3・4）

1. **母数の語を見る**：道具名・業務名・対象そのものの単体（例：「エクセル」「パワーポイント」）。検索数が多いほど、それを毎日使い、困っている人が多い。ラッコで、母数の語と切り口の語（例：「excel ai」）を同じ1回で取る
2. **悩みの種類を確かめる**：検索数が同じように大きくても、悩みの種類によって作るべき動画が違う。**種類は推測で決めず、その語で YouTube を検索し、上位にどんな動画が並ぶかで確かめる**（`search_compare.ts "語"`。1語約100ユニット。回数を決めてから実行。並び順は既定の関連度順にする。再生数順だと、関係のない話題の動画や海外の動画が上に来る）。ラッコのサジェスト（`suggest-keywords`）やよくある質問（`question-search`）は、言い回しを集める補助に使う。**英語の製品名（例：「teams」「outlook」）は、YouTube では日本に絞っても海外の動画が混ざる**ので、カタカナ（「チームズ」）や日本語の組み合わせ（「teams 会議」）でも検索して比べる。ラッコの数字は地域 Japan・言語 Japanese なので、英語の語でも日本の検索数
   - **たどり着きたい**：ログイン、ダウンロード、開き方など、その道具に入るための検索。検索数は大きいが、動画で解く悩みではない。YouTube の上位も、業務と関係のない動画になる（例：「teams」「outlook」）
   - **操作がわからない**：使い方、設定、エラー。解くのは手順の解説で、「楽にしたい」という欲求とは別
   - **作業が重い**：その道具で毎日している作業の手間・時間。「楽にしたい、時間を減らしたい」という欲求で、AIや効率化の動画が刺さる。YouTube の上位に「時短」「効率化」の動画が並ぶ（例：「エクセル」）
   - チャンネルの提供価値に合う種類の悩みだけを題材の候補にする（例：業務効率化のチャンネルなら「作業が重い」）。共通する悩みを1文にする（例：「毎日のExcel作業に時間を取られている」）
2b. **悩みを掘る**：悩みの種類が合う母数の語は、上位の動画の中身とコメントから、具体的な悩みを読む
   ```bash
   node scripts/search_compare.ts "語"      # 関連度順（取得済みなら不要）
   node scripts/pain_research.ts "語"       # 上位10本のチャプター・冒頭の発言・コメント → data/_pains/<語>.md。通常の動画（3分以上）5本の全文を data/_pains/<語>/ に保存（約11ユニット＋文字起こし10本）。5本は、再生の多い2本を必ず含め、残りは検索順位の順、同じチャンネルは2本まで
   # 上位にショートが多い語（例：道具名）は --top 20 にして、通常の動画を5本確保する
   ```
   - **タイトルと冒頭の発言は「作り手が読んだ悩み」**。冒頭で名指しされる悩み（「会社で○○しか使えない」「○○を使いこなせていない」）は特に強い手がかり。伸びた動画ほど、その悩みが多くの人のものだったと読める
   - **コメントは「視聴者自身の悩み」**。「悩み・質問の候補」を読み、悩みを型に分ける。型ごとに根拠（コメントの件数・いいね・代表的な引用、冒頭で名指しした動画）を書く
   - コメントが1本の動画に偏っていないか、件数も書く（少なければ「手がかり」として扱う）
   - **冒頭やチャプターだけで判断しない。5本は文字起こしの全文を読む**（よく見られている答えと、いろいろな作り手の答えを読むため、選び方は上のとおり。読まなかった動画で判定が変わりそうなら、`--full` を増やして読み足す）（本文の途中で答えていて、チャプターに出ていないことがある）。1本ずつエージェントに任せて並行で読み、どの動画にも同じチェック項目（悩みの型ごとの判定・時刻・引用、前提［有料版／無料版／個人／会社］、情報量、他にない情報、物足りない点、導線）で報告させ、突き合わせる

2c. **応えきれているかを見る**：悩みの型ごとに、上位の動画がどこまで答えているかを見る。まだ答えられていない所が、新しい動画の入る余地になる
   - **答えがあるか**：上位5本の全文で、その悩みに答えている動画と時刻を探す（チャプターは目次として使うだけ）。「十分に答えている」「触れる程度」「触れていない」を分け、どれも触れる程度以下なら**空白**（まだ誰も答えていない）
   - **情報量が足りているか**：コメントに「実例が欲しい」「もっと詳しく」があれば**浅い**。尺・手順の具体さ・実例の有無も見る。長い動画や「全手順」「○選」で伸びている題材は、深さが求められている
   - **前提がずれていないか**：「無料版では使えない」「会社では入れられない」などは、動画の前提（有料版・個人利用など）と視聴者の状況が**ずれている**しるし
   - **不安に答えているか**：「大丈夫でしょうか」「心配」「気をつけないと」に答える動画がなければ空白
   - **古くなっていないか**：「消えました」「できなくなった」は、アップデートで答えが**古い**しるし
   - **他の人が紹介していない有益な情報**：運用者の現場の知見（顧客の実例、問い合わせで聞かれること、実務の落とし穴）で、上の空白・浅さ・ずれ・不安に答えられるものを書き出す。これがチャンネルの差別化になる
   - 型ごとに「十分」「浅い」「空白」「ずれ」「古い」をつけ、**空白・浅い・ずれ・古い × 母数が大きい × 提供価値に合う**ものを企画の最優先にする。結果は `data/_pains/<語>_分析.md` に書く（悩みの型／根拠のコメント／答えている動画／判定／自分が答えられること）
   - **突き合わせ表**：行を動画（タイトルのリンク、チャンネル・再生・尺・公開）、列を悩みの型にし、各セルに「十分／触れる／—」を書く。最後の行に総合（十分・空白・浅い・ずれ・古い）を置く。部分的にしか答えていない動画は「十分※」とし、どの範囲に限るかを注に書く。表の下に、全文を読んでわかったこと（前提、実例の有無、導線）と、運用者が差別化できる所を書く
   - コメントの引用は、悩みの型・コメント・**書かれていた動画（タイトルのリンク）**の3列で出す
   - **全文を読むエージェントへの指示のひな形**（1本に1エージェント、並行で起動）：

     ```
     YouTube 動画の文字起こしの全文を読み、視聴者の悩みにどこまで答えているかを判定してください。
     ファイルを最初から最後まで全部読むこと（冒頭や一部だけで判断しない）。ファイルは書き換えない。
     ファイル: data/_pains/<語>/<順位>_<動画ID>.txt（[m:ss] は時刻。自動字幕なので誤変換がある）
     チェックする悩み: A〜（2b で作った悩みの型を並べる）
     返す形（1,500字以内）:
     1. 動画の流れ（時刻つき5〜8行）
     2. 前提（有料版／無料版／個人向け／会社向け。明言があれば時刻と引用）
     3. 悩みごとの判定（十分に答えている／触れる程度／触れていない、時刻・1〜2文の要約・15字以内の引用）
     4. 情報量（実演・手順・プロンプト例・実例の数字）
     5. 他の動画にはなさそうな有益な情報
     6. 視聴者が物足りなく感じそうな点
     7. 最後の導線（セミナー・LINE・研修など）
     ```
   - エージェントの報告は `data/_pains/<語>_全文.md` にまとめて残し、突き合わせ表を作る。チャプターや冒頭だけの判定から変わった所（例：本文で触れていた、タイトルの約束を果たしていない）も書く

3. **悩みを主語にして動画を作る**：タイトルと冒頭は、検索語ではなく悩み（と解けた後の状態）で書き、道具名は従にする（例：「AIでExcel業務を秒で終わらせる【ChatGPT・Copilot・Claude】」）。検索語そのもの（「excel ai」など）がタイトルに入っているか、検索されているかは問わない
4. **切り口の語で需要を判断しない**：「excel ai」のような組み合わせの検索が少なくても、母数の語の悩みが大きければ、「自分から検索はしないが、ホームに出れば押す」人が大勢いる。こういう動画は、おすすめ（ブラウジング機能）で新しい視聴者に広がる

- 例：Excel の業務を AI で片づける動画が、おすすめから新しい視聴者に大きく広がったことがある。切り口の語（「excel ai」）の検索は小さかったが、母数の語（「エクセル」「excel」）は大きく、YouTube で「エクセル」を検索すると上位は時短の動画だった。検索語ではなく、Excel を毎日使う大勢の人の「作業が重い」悩みに届いた
- 振り返り（C3）では、伸びた動画について「どの母数の語の、どんな種類の悩みに答えたか」を書く。企画では、母数の語が大きく、チャンネルの提供価値に合う種類の悩みがあり、その悩みにまだ答えている動画が少ない題材を探す（YouTube の上位の動画の本数・新しさ・登録者の少ないチャンネルが入っているかはパートBの見方で見る）

### C6：題材の候補を自律的に検証する

C5 を、たくさんの語について Claude が止まらずに回す。ユーザーに確認するのは、最初の予算だけにする。

**最初に聞くこと**

- 種になる語、またはこのチャンネルが解く悩み（例：「AIで毎日の業務を楽にする」）
- 1回の予算：ラッコのクレジット（既定100。50語ごとに50クレジット）。YouTube API は1日の上限（10,000ユニット）の範囲なら確認不要（CLAUDE.md）。どちらも、語の数から先に見積もり、超えそうなら語を絞ってから始める

**予算の中で、止まらずに回すこと**（途中でユーザーに確認しない）

1. **候補の語を出す**：種から、母数の語（道具名・業務名・対象）と切り口の語（母数の語×チャンネルの解き方）を出す。英語の製品名は、カタカナと日本語の組み合わせも入れる。自分のチャンネルの YouTube検索語（`own_keywords.ts`）と、伸びた動画の題材（C3）も種にする
2. **ラッコで検索数を取る**：`rakko_cache.ts missing` → キャッシュにない語だけを1回にまとめて送る → `put`
3. **YouTube の検索結果から悩みの種類を判定し、悩みを掘る**（C5 の 2・2b・2c）。語が複数あるときは、`pain_research.ts` で材料を集めたあと、**語ごとに1エージェント**を並行で起動し、2b（悩みの型）と 2c（5本の全文の突き合わせ）を任せて `data/_pains/<語>_全文.md`・`<語>_分析.md` に書かせる。エージェントには SKILL.md の C5 を読ませ、チャンネルの提供価値を判断の観点として渡す。戻った結果は Claude が確かめ、語をまたいで比べる：母数の語と主な切り口の語で `search_compare.ts "語"`（関連度順、直近365日）。上位の動画のタイトル・尺・チャンネルから、C5 の3つの種類（たどり着きたい／操作がわからない／作業が重い）のどれが多いかを判定し、**根拠にした上位の動画のタイトルを2〜3本残す**
4. **競合の状況を見る**（パートBの見方）：上位に直近の動画があるか、登録者の少ないチャンネルが「再生÷登録者」の高い動画で入っているか
   - **競合のチャンネルで伸びた動画を見る**：検索結果に出たチャンネルから、同じ立ち位置（例：企業向けの業務AI）の5〜10チャンネルを選び、`fetch_channel.ts` で全動画を取る（1チャンネル数〜数十ユニット）。直近半年の通常動画を、**同じチャンネル・同じ時期の中央値との比**で並べ、3倍以上の動画を集める（登録者の違いを消すため、再生数そのものでは比べない。公開日 2026-08-27 の前後で中央値を分ける）。伸びた動画・伸びなかった動画の題材を型にまとめ、悩みの種類と母数の語で読む。競合で繰り返し伸びている型は、候補の順位を上げる根拠にする。直近に同じ題材で伸びた動画があれば、追い風（タイミング）の材料として書く
5. **自分のチャンネルと照らし合わせる**：同じ種類の悩みに答えた過去の動画の成績（新規の割合、クリック率とインプレッション、維持率の形）。チャンネルの提供価値に合う種類か
   - **顧客の声を重く見る**：目的が問い合わせ・契約なら、運用者から聞いた問い合わせの傾向（C0）を、検索数や競合の伸びより重い根拠にする。検索・競合・問い合わせの3つが同じ題材を指していれば、「伸びる題材」と「契約につながる題材」が重なっているので、最優先の候補にする
   - **入口と導線を分ける**：タイトルは使う人本人の得（例：「秒で終わる」「全手順」）を主語にして入口を広く取り、組織の悩み（例：「定着しない」「管理職向け」）は主語にしない（競合でも伸びにくい）。中身の後半で、会社で進めるときのポイントに触れ、問い合わせへの導線を作る
6. **候補ごとに仮説と予測を書き、今あるデータで判定する**：例「O3：『パワーポイント』の作業が重い悩みを主語にした動画は、Excelの動画と同じくおすすめで新規に広がる。予測：インプレッション10万回超でもクリック率4.5%以上」。判定は、公開前なので多くが「未検証」。否定できるものは否定する（例：上位が業務と無関係なら候補から外す）

**出力**

- `data/<slug>/topics/<YYYY-MM-DD>.md`：候補の順位表（語／母数の語の検索数［ラッコ］／悩みの種類と根拠の上位動画［YouTube API］／競合の状況／自分の過去の動画での成績／仮説と予測／順位の理由）。外した候補も、外した理由と一緒に残す
- 台帳：上位の候補を O番号で書く（予測つき）
- 返答：上位3つと、それぞれを選んだ理由を短く。使ったクレジットとユニット。ユーザーの判断が要る点だけを問いにする（例：「顧問先でよく聞くのはどちらの悩みか」）

**公開後**

- ユーザーが候補から動画を出したら、公開前に予測を台帳に書き（C4）、公開7日後に C2 を回して判定する。予約（スケジュール）で自動にしてもよい

## 検証の幅を広げる

1つのチャンネルで支持された仮説は、そのチャンネルの条件（演者の知名度、開設時期、相場の追い風）のもとでしか確かめられていない。**支持された仮説ごとに、次の3つの問いを立て、別のチャンネルやキーワードの検索結果で確かめる。**

| 問い | 例（「話題の言葉の解説が伸びる」が支持された場合） | 確かめ方 |
|---|---|---|
| ① 今も、この型で伸びているチャンネルがあるか | 直近数か月、話題の言葉の解説で伸びているチャンネルはあるか | パートBで、その型の語の検索結果の「直近30日」の動画を見る |
| ② 著名人でなくても伸びるか | 演者に知名度がなくても再生を取れているか | パートBで、登録者10万人未満のチャンネルの「再生÷登録者」を見る。候補はラッコで演者名の検索数も確かめる |
| ③ 最近始めたチャンネルでも伸びるか | 開設から1〜2年のチャンネルでも同じ型で伸びているか | パートBで、開設2年以内のチャンネルを見る。深掘りする価値があればパートAを行う |

- パートBの検索結果から見つかった「①〜③に当てはまるチャンネル」を、次に分析するチャンネルの候補にする。ほかに、ユーザーの指定、ベンチマークの概要欄に出てくるチャンネル、`scripts/find_similar.ts` も使う
- 候補は表（チャンネル／登録者／開設／直近の再生／どの問いに答えるか）で見せ、ユーザーに選んでもらう
- ③まで支持された仮説が、クライアントのチャンネルで再現できる見込みの高いもの
